INFINITUM:THE LAST SCALE
Complete Game Design, Narrative, Art, Technical Architecture, Production & Astra Build Bible

THE ONE-SENTENCE PITCHA short first-person 3D mind-bender where the player enters a forbidden miniature world, learns to rewrite scale, gravity and causality, then discovers that every “smaller” world was actually part of something vastly larger.

Designed as a 15–30 minute premium-feeling browser experience that prioritizes unforgettable visual transitions, tactile mechanics, mystery, and a complete ending over map size or content volume.

READ THIS FIRSTThe biggest project risk is not technical difficulty; it is scope explosion. The experience should feel huge while the implementation stays compact. Reuse one environment, transform it aggressively, and make transitions carry the spectacle.

1. Product vision and non-negotiable pillars
INFINITUM is not an “open play and go” sandbox. It is a deliberately paced, authored experience with a mystery, escalating mechanics, changing objectives, failure/recovery states and a final payoff. The player should always understand that they are moving toward an answer, even when they do not yet understand the world.
1.1 The player fantasy
The fantasy is: “I am learning to break the rules of reality faster than the world can contain me.” The player begins powerless and curious. By the end, they can manipulate perspective, gravity and their own past actions to perform combinations that looked impossible at the start.

2. Audience, platform, session and success criteria
2.1 Audience
Primary: players who share visually surprising indie games, puzzle experiences, short horror/surreal experiences, Three.js/WebGL experiments and “play this without context” links. Secondary: technically curious players who enjoy breaking systems and speedrunning compact puzzle games.
2.2 Session assumptions
First-time completion: target 15–30 minutes.
No account required.
Load-to-control target: as fast as practical; show progress and allow audio choice before pointer lock.
Checkpoint recovery should return a failed or disconnected player to the current puzzle cluster, not the beginning.
Designed first for desktop Chromium-class browsers. Wider compatibility is a shipping consideration, not a reason to reduce the visual identity.

2.4 Minimum viable “mind-blow” checklist
A seamless scale transition that changes the perceived size of the world without a visible loading cut.
A gravity transition where architecture becomes traversable in a new orientation.
A temporal Echo that visibly repeats a prior player action and becomes mechanically useful.
A combined puzzle using all three mechanics.
A final environment collapse/reveal that changes the interpretation of earlier scenes.

3.2 Optional secrets
Secrets should deepen interpretation without adding required systems. 4. Narrative, world rules and reveal structure
4.1 Premise
The player awakens in a sterile, almost sacred chamber containing one impossible object: a transparent sphere with a living city inside it. The only explicit instruction is not to enter. The prohibition creates immediate purpose: the sphere is the obvious objective and the first act of disobedience defines the player’s relationship with the world.
4.2 The Curator
The Curator is not introduced as a humanoid boss. It is the organizing intelligence that keeps scales, timelines and frames of reference separated. Early evidence appears as environmental corrections: a door moves after being solved, a line of text rewrites itself, a gravity anchor turns away, an Echo is erased. Only near the end does the player understand that the environment itself has been the antagonist.

5. Core mechanic specification: Perspective Scale
5.1 Player rule
If an object visually aligns with a target frame from the player’s camera, the player can lock that perceived relationship. The game then changes the object’s physical scale and/or placement so the relationship becomes real.
5.2 Interaction model
Aim at an eligible object. It receives a subtle silhouette/reticle response.
Hold the Manipulate input to “capture” the object in perspective space.
Move/look until the object overlaps a compatible frame or anchor.
When alignment is valid, show a calm confirmation cue — not a giant UI prompt.
Release/confirm. Animate scale/position transformation over 200–500 ms with sound and temporal distortion.
5.3 Implementation strategy
Do not attempt arbitrary world-scale ray-magic for every mesh. Use authored ScaleAnchors and ScaleTargets. The camera defines a ray/frustum relationship; eligible objects have bounded scale ranges and permitted target sockets. The system calculates the desired apparent angular size or screen-space fit, then resolves a safe world transform and asks physics to validate the destination.
Component
Responsibility
ScaleManipulationSystem
Owns selection, capture, validation, transform interpolation.
ScaleableComponent
Object metadata: min/max scale, pivot, collider regeneration mode, allowed anchors.
ScaleAnchor
Defines compatible target plane/volume and completion rule.

Measures projected bounds / alignment tolerances.

Updates collider safely after a completed scale change.

5.4 Safety constraints
Never allow scaling to zero, negative scale, or collider sizes outside tested ranges.
Freeze or switch rigid bodies to kinematic during the short transformation.
Validate occupancy before committing a destination.
If the final transform intersects critical geometry, reject with readable feedback.
Puzzle-critical objects have a one-button local reset.
5.5 Showcase puzzle
A monumental bridge is visible kilometers away through a narrow doorway. The player captures it when it appears small, aligns it inside a socket near the door, and releases. The “distant” bridge becomes a carryable architectural piece. Later the same rule is reversed: a small object is expanded until it becomes a traversal surface.
6. Core mechanic specification: Gravity Reorientation
6.1 Player rule
Gravity belongs to the current local frame, not to the entire universe. Activated Gravity Anchors define a new up/down vector. The player, selected dynamic objects and specific world groups transition smoothly into the new frame.
6.2 Feel goals
The camera should preserve player comfort: rotate with easing and keep a stable horizon during most traversal.
The world can rotate more dramatically than the camera.
Transitions should feel deliberate, heavy and spatial — not like the player camera suddenly rolls 90 degrees.
Use audio low-frequency movement and environmental particles to sell the new down direction.
6.3 Technical design
Rapier’s character controller supports a configurable up vector, which is useful for local gravity traversal. The game still owns gravity acceleration and camera orientation. Treat player locomotion, physics gravity and visual-world rotation as related but separate concerns so authored sequences can choose the safest representation.

6.4 Showcase puzzle
The player enters a vertical canyon between skyscrapers. An anchor rotates gravity toward one building facade. That wall becomes the street. A second anchor makes the former sky a traversable plaza. The same geometry becomes three different paths without building three separate levels.
7. Core mechanic specification: Echo / Temporal Self
7.1 Player rule
Within defined Temporal Zones, the player can reset a short local sequence. The previous attempt becomes an Echo that repeats recorded movement and important actions while the current player begins again. The Echo is not initially AI; it is a deterministic playback system.
7.2 Why zones, not global time travel
Limiting Echo recording to authored zones keeps memory, physics state, puzzle resets and debugging manageable. It also makes the mechanic readable: entering a zone communicates “this room can be solved across attempts.”
7.3 Recording model

7.4 Fixed simulation
Run gameplay recording and physics on a fixed simulation step. Rendering interpolates between states. This prevents recording density from changing with frame rate and makes Echo timing predictable. Avoid storing an entire world snapshot every render frame.
7.5 Echo visual language
Semi-transparent but not cliché hologram blue. Use a refractive/temporal edge treatment tied to the project’s material language.
Echo footsteps are filtered and slightly time-stretched.
Interaction points leave a very short-lived temporal imprint.
When multiple Echoes overlap, prioritize silhouettes and depth readability over bloom.
7.6 Failure handling
Cap simultaneous Echoes per zone (initially 3–5).
Provide Clear Echoes / Reset Zone in pause or diegetic control.
If an Echo cannot complete a recorded interaction because state diverged, it should fail visibly and continue its path rather than hard-lock the game.
Puzzle completion commits the zone and discards unnecessary recordings.

8.2 The three-rule final lock
Recommended sequence: create Echo A to hold an orientation stabilizer; reset. Current player changes gravity and reaches a perspective balcony; from that frame, shrink a monumental key into a movable object; place it into a socket while Echo A maintains the field. A Curator correction then partially rotates the structure, forcing a final timed traversal using the same established rules — no new mechanic.
8.3 Hint system
Do not use a chatty tutorial character. Use layered hints: first visual emphasis, then environmental movement, then a compact optional text hint after a defined inactivity period. Hints must state the relevant rule, not the solution path.

9.3 Asset economy
A small library of excellent modular pieces beats a large generic asset pack: slabs, ribs, monoliths, frames, bridges, glass volumes, cable/rail elements, one or two hero sculptures, procedural city towers, and a few physically based surface families. The world identity comes from scale, composition, lighting and transformation.
10. Art direction and visual identity
10.1 Visual thesis
“Monumental precision being invaded by impossible physics.” The world begins clean, controlled and almost sacred. As the player breaks rules, the same forms become fractured, refracted and temporally misaligned.

11. Rendering, lighting, materials, shaders and post-processing
11.1 Renderer choice
Recommended architecture: evaluate Three.js WebGPURenderer early because it can use WebGPU and automatically fall back to a WebGL 2 backend. It also aligns with Three.js’s newer TSL/node-material and post-processing direction. However, WebGPURenderer is still described by Three.js as experimental, so keep a renderer abstraction and validate every required effect on the target browser set before depending on it.
COMPATIBILITY NOTEWebGPU itself is still not universally available across all major browser/device combinations and requires a secure context. Ship with tested fallback behavior and a visible compatibility path rather than assuming every player has WebGPU.

11.3 TSL / custom shader priorities
Echo material: depth-readable temporal surface with edge phase offset.
Scale-lock shader: world-space/object-space patterns that visually stretch as perspective is committed.
Curator correction: geometry/material phase transition using masks, not just screen noise.
Sky/void: procedural stars, scale-dependent parallax and controlled gravitational distortion.
Surface detail: triplanar/procedural breakup for huge architecture to avoid obvious texel scale.
11.4 Lighting strategy
Prefer a few authored lighting states rather than many dynamic lights. Use environment lighting, directional/area-like hero sources, emissive architecture and baked/lightmapped contributions where practical. Every chapter transition can crossfade light rigs and material parameters to make reused geometry feel new.

12.1 Rule: never steal control for too long
The strongest spectacle happens while the player is still participating. Use short guided camera influence, temporary movement limits or authored look targets rather than long non-interactive movies.

12.3 Camera comfort
Default FOV should feel modern but not fisheye; allow user adjustment.
Avoid sudden forced roll in first person.
Reduce head bob; use acceleration, landing and subtle camera impulse for weight.
For huge scale transitions, animate world/camera relationship with stable focal anchors to reduce motion sickness.
Provide a Reduced Camera Motion option that removes/shortens roll, shake and aggressive FOV changes.
13. Audio, music and haptics-equivalent feedback
13.1 Audio identity
The soundscape should communicate scale before the player understands it visually. Use long architectural reverberation, low-frequency structures, distant mechanical resonance, filtered transient detail and near-silence before major transformations.

13.3 Web Audio approach
Use Web Audio for spatialization, filters, buses and procedural layers. Require a clear user gesture before audio starts. Keep a master compressor/limiter conservative; prioritize headroom because layered finale effects can clip quickly.
13.4 No-controller “haptics”
On keyboard/mouse, perceived impact comes from synchronized audio transient, camera impulse, animation easing, screen-space response and environmental secondary motion. Treat these as one feedback event authored through a central FeedbackSystem.

15.3 Checkpoint model
Checkpoint at chapter boundaries and before the final combined puzzle. Save only stable high-level state: chapter ID, puzzle completion flags, settings and optional secrets. Do not serialize the entire physics scene. On restore, rebuild the authored chapter state deterministically.
15.4 Error recovery
Every puzzle room has a local reset.
Detect player falling outside valid bounds and restore to last safe transform.
If WebGPU initialization fails, retry/fallback gracefully.
If audio initialization fails, continue silently with a visible settings note.
If a checkpoint schema changes between builds, migrate or safely reset progression rather than crashing.
16. Technical architecture and repository structure
16.1 Architecture principles
Systems communicate through explicit interfaces/events, not global mutable state.
Rendering objects are not the source of truth for gameplay state.
Physics, gameplay simulation and rendering have clear update phases.
Every entity that participates in recording/puzzles gets a stable ID.
Major mechanic code is independent enough to test in a sandbox scene.
Debug visualization is a first-class feature, not an afterthought.

16.4 Event design
Use semantic events such as InteractionStarted(entityId), GravityChanged(anchorId, up), ScaleCommitted(entityId, anchorId, transform), EchoReset(zoneId), PuzzleSolved(puzzleId). Timeline recording can serialize selected semantic events without coupling itself to every mechanic implementation.
17. Simulation, physics, timeline and world-state architecture
17.1 Physics
Rapier is a WebAssembly physics engine available for JavaScript. Initialize it asynchronously during boot. Use fixed rigid bodies for level collision, dynamic bodies sparingly for hero interactions, and position/velocity kinematic bodies for controlled moving geometry. Keep render and physics transforms synchronized through adapters rather than mixing direct writes throughout the codebase.
17.2 Character
Use a capsule collider. The player motor asks the character controller for corrected movement and owns jump/gravity. Collision events feed footsteps, impacts and interaction logic. For changing gravity, treat local up as explicit player state and update movement basis consistently.

17.4 Determinism expectations
Do not promise full deterministic physics replay across browsers. Echoes should be deterministic enough at the gameplay layer because their body path can be driven by recorded/interpolated transforms and semantic interaction events. Puzzle-critical interactions should be tolerant of small divergence.
18. Asset pipeline, procedural content and content authoring
18.1 Asset principles
Prefer glTF/GLB for authored 3D assets.
Batch/instance repeated architecture.
Atlas or reuse textures where it reduces draw calls without visibly harming hero surfaces.
Use KTX2/Basis-style compressed textures where pipeline support is stable.
Use Draco or Meshopt only after profiling load size/CPU tradeoffs.
Keep source assets outside the runtime tree; export optimized game-ready files.
18.2 Procedural content
Procedural generation is a production tool, not the game structure. Good uses: tower variations, windows, cables, star fields, floating fragments, instanced debris and controlled architectural repetition. Bad use: generating the critical puzzle path or replacing authored composition.
18.3 Content data
Author chapter/puzzle settings as typed data instead of hardcoding values throughout scene scripts. A ChapterDefinition can reference spawn point, lighting state, active world groups, objective text, checkpoint ID and transition sequence. Validate data at startup in development builds.

19.1 Performance philosophy
Frame-time stability is part of the graphics. A beautiful 40–55 FPS experience with stutter feels cheaper than a slightly simpler stable 60 FPS presentation. Profile CPU and GPU separately and budget spectacle as temporary spikes, not permanent cost.

A Steam/native port should follow evidence of audience demand, not precede the browser proof-of-concept.

Appendix E — Current technology notes (September 2026)
The following notes are included to keep the build plan aligned with current official documentation. Pin and verify actual package versions when initializing the repo; the game bible intentionally specifies architecture more strongly than exact versions.
Three.js WebGPURenderer: Three.js documents WebGPURenderer as its next-generation renderer. It targets WebGPU by default and can fall back to a WebGL 2 backend. WebGPU: MDN describes WebGPU as limited availability and secure-context-only. Source: MDN WebGPU API
Rapier: Rapier provides JavaScript/WASM 3D physics and a kinematic character controller with obstacle sliding, slopes, stairs, moving-platform support and configurable up vector. Source: Rapier JavaScript character controller
